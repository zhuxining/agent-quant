## Context

- ✅ Multi-Agent 交易系统已完成基础架构（5 个 Agents + Trading Team）
- ✅ AkShare 数据源已集成（A 股行情、新闻、基本面）
- ✅ Workflow V2 已实现（并行数据获取 + Team 执行）

**核心关切**：
1. 回测基于模拟交易，认为没有意义
2. 希望去除虚拟交易/回测，仅作实盘分析
3. 需要长期规划，系统性完善项目

## 核心问题分析

### 问题 1：回测的定位和价值

**当前实现**：
```
app/backtest/engine.py
├─ 获取历史数据 (end_date 参数)
├─ 调用 Workflow (实时运行 Multi-Agent)
├─ 记录交易结果
├─ 计算净值曲线
└─ 生成报告
```

**用户的质疑**：
- 回测是基于"模拟交易的成交情况来回测的"
- "历史业绩、历史新闻这些不好处理，也不能很好的模拟手续费花点"
- "所以我想去除这部分，仅作实盘分析"

**我的分析**：
1. **回测的本质**：回测应该是**向量化**历史数据验证，而不是**重复执行实时流程**
2. **当前问题**：
   - 每次回测都调用 LLM（慢、贵、不稳定）
   - 没有历史新闻数据（无法验证新闻影响）
   - 没有基本面历史数据（无法验证财务分析质量）
   - 模拟交易太简化（无手续费、滑点）
3. **矛盾点**：用户既想"去除模拟交易"，又想"验证 prompt 策略"——两者是关联的

### 问题 2：架构定位模糊

**当前混淆**：
| 模块 | 当前状态 | 问题 |
|------|---------|------|
| 虚拟交易 | account.py/order.py/position.py | "模拟交易"还是"实盘模拟"？ |
| 回测 | engine.py | 基于模拟交易，但应该基于历史数据 |

**需要明确**：
- 实盘分析 vs 模拟交易的区别
- 回测的目的和验证方式
- 各模块的职责边界

## 方案设计

### 方案 A：纯实时分析（倾向方向）

#### 架构
```
实时分析系统
├─ [市场数据获取] (AkShare/Longport 并行)
│   ├─ 实时行情
│   ├─ 实时新闻
│   └─ 实时基本面
├─ [Multi-Agent Team 分析]
│   ├─ 新闻情绪 Agent
│   ├─ 技术分析 Agent
│   ├─ 基本面 Agent
│   ├─ 决策综合 Agent (Team Leader)
│   └─ 风控 Agent
├─ [人工/实盘验证]
│   └─ 交易建议执行（手动或半自动）
└─ [文档与监控]
    ├─ Agent 性能监控
    └─ 交易建议记录
```

#### 改动范围
| 模块 | 操作 | 保留/移除 |
|------|---------|--------|
| AkShare 数据源 | ✅ 保留 | - |
| Longport 数据源 | ✅ 保留 | - |
| Multi-Agent Agents | ✅ 保留 | - |
| Workflow V2 | ✅ 保留 | - |
| **虚拟交易** | ⚠️ 保留但降级 | 改为"实盘模拟模块" |
| **回测引擎** | ⚠️ 保留但重构 | 重构为"策略回测引擎" |
| 历史新闻 | ❌ 移除 | 等待外部数据源 |
| 历史基本面 | ❌ 移除 | 等待外部数据源 |

#### 优势
- ✅ 聚焦核心价值：实盘分析
- ✅ 简化架构，减少混淆
- ✅ 快速交付（1-2 周）

#### 缺点
- ⚠️ 无法系统性量化验证策略（需要向量化回测）
- ⚠️ 仍保留部分模拟代码，可能造成混淆
- ⚠️ 缺少历史数据支持（需要外部集成）

### 方案 B：保留双轨制（推荐）

#### 架构
```
双轨制系统
┌─────────────────────────────────────────────────┐
│            [实时交易系统]              │      [策略回测系统]         │
│                                       │                               │        │
├─────────────────────────────────────────────────┤
│ Market Data (AkShare/Longport)          │  Market Data (历史向量)        │
│          ↓                            │             ↓                    │
│ Multi-Agent Team                    │    向量化策略引擎           │
│     (实时分析)                        │        ↓                    │
│          ↓                            │   [历史数据加载]           │
│     ↓                            │        ↓                    │
│  Paper Trading                      │    快速回测引擎              │
│     (手续费/滑点)                     │        ↓                    │
│          ↓                            │        ↓                    │
│ 交易执行                           │    参数优化                    │
│          ↓                            │        ↓                    │
│     报告系统                          │        ↓                    │
└─────────────────────────────────────────────────┘
                                       │
                             [文档与监控]
```

#### 改动范围
| 模块 | 操作 | 保留/移除 |
|------|---------|--------|
| AkShare 数据源 | ✅ 保留 | - |
| Longport 数据源 | ✅ 保留 | - |
| Multi-Agent Agents | ✅ 保留 | - |
| Workflow V2 | ✅ 保留 | - |
| **虚拟交易** | ✅ 增强 | 重命名为"Paper Trading 模块" |
| **回测引擎** | ✅ 保留 | 重构为"策略回测引擎" |
| **回测报告** | ✅ 增强 | - |
| **历史数据加载** | ✅ 新增 | 从文件/数据库加载 |
| **参数优化系统** | ❌ 移除 | 后期可选 |
| **报告系统** | ❌ 移除 | 后期可选 |

#### 优势
- ✅ 明确分工：实时交易 vs 策略验证
- ✅ 保留回测能力，但重构为真正的向量化回测
- ✅ 可以逐步验证 Multi-Agent 的质量
- ✅ 两个系统互为补充，减少单一系统的压力
- ✅ 保留历史数据加载路径

#### 缺点
- ⚠️ 架构复杂度增加（双轨制）
- ⚠️ 需要明确两个系统的使用场景
- ⚠️ 需要设计数据共享机制

### 方案 C：增强 Paper Trading（中期增强）

#### 增强功能
1. **真实交易特性**
   - 手续费计算（按成交金额或按股）
   - 滑点模拟（0.01%-0.1%）
   - T+1 交易规则（成交优先）
   - 资金使用限制（保证金模式）
   - 市价冲击模拟（大额订单影响价格）

2. **订单类型扩展**
   - 条件单（止盈/止损自动触发）
   - 冰山订单（大额拆分执行）
   - 改限单（价格/数量限制）

3. **持仓管理增强**
   - 分批减仓（避免冲击）
   - 动态调仓（基于波动率）
   - 锁定机制（防止异常交易）

#### 优势
- ✅ 快速实现（2-3 周）
- ✅ 接近实盘体验
- ✅ 不影响实时分析系统
- ✅ 为真实交易做"纸上练习"

#### 缺点
- ⚠️ 仍然是"模拟"，无法真正验证策略
- ⚠️ 复杂度与价值是否匹配
